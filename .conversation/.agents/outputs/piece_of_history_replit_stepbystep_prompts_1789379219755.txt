STEP 1 — Kickoff & Architecture Plan
Start every build with a plan before any code gets written, so the agent commits to the right architecture up
front.
Copy — paste into Replit Agent:
You are the lead product engineer for a Replit project called "Piece of History."
Core tagline: "Every day disappears. Some days become history."
Core mechanic: one "day" is active at a time. Each participant submits a short
story and an optional website URL, then makes real, non-refundable payments to
compete to be #1. A participant's rank is the SUM of every payment they have
made that day (a running total), not just their latest single payment. At
exactly 23:59:59 (server time, configurable timezone) the day freezes and
whoever has the highest running total wins. The win, and every payment
collected that day, goes to the site owner. No platform fee, no refunds for
non-winners, no proxy bidding.
Visual direction: "Snowy Blue" — white and pale icy-blue backgrounds, navy
text/buttons, subtle snowflakes and mountain illustrations, playful
micro-copy. Clean and fast, never visually heavy.
Do NOT build: social features (followers/likes/comments/chat), subscriptions,
points, badges, NFTs/crypto, AI-generated stories, a marketplace, or proxy
bidding. Keep this a tiny, memorable side project with one core mechanic.
Recommended stack: Next.js (App Router) + TypeScript + Tailwind CSS, Replit's
built-in PostgreSQL database with Prisma ORM, NextAuth.js for auth, Razorpay
for payments behind a small provider-abstraction layer.
Before writing any code: produce (1) a short architecture overview, (2) a full
database schema (Users, DailyPiece, Story, Bid-as-ledger, computed
ParticipantStanding, optional AuditEvent), and (3) a state-transition diagram
for a day going active → receiving payments → closing → archived. Wait for my
confirmation before implementing.

STEP 6 — Cumulative Bidding Engine + Razorpay Payments
The core mechanic: every payment is real, charged immediately, and adds to a running total that determines
rank.
Copy — paste into Replit Agent:

===== PAGE 4 =====
Implement the cumulative real-money bidding engine for Piece of History:
1. Integrate Razorpay checkout for a payment of any amount ≥ the configured
minimum. Never mark a payment as successful from the client — only a verified
server-side Razorpay webhook may mark a Bid as captured.
2. When a payment is verified as captured, in a single database transaction:
insert the immutable Bid row, recompute that user's running total for the day
(SUM of all their captured Bids today), and recompute the day's current
leader (highest running total; on an exact tie, whoever reached that total
earliest keeps or gains #1). Use row-level locking on the DailyPiece so two
simultaneous payments can never both believe they are #1.
3. Example to satisfy: A pays $5 (A leads at $5). B pays $10 (B leads at $10).
A pays $6 more (A's total is now $11, so A leads again). Write an automated
test that reproduces exactly this sequence and asserts the leader at each
step.
4. Also write tests for: a payment below the minimum increment is rejected, a
duplicate/replayed webhook cannot double-count a payment, and two concurrent
payments that would tie are resolved deterministically.

STEP 8 — Day-Close Job (23:59:59 Freeze & Winner Selection)
The scheduled job that ends the day and locks in the winner, safely.
Copy — paste into Replit Agent:

===== PAGE 5 =====
Implement the day-close operation as an idempotent database transaction:
given an active DailyPiece whose closing_timestamp has passed, lock the row,
determine the winner (highest running total, tie-break by earliest timestamp
reaching that total), set status to "closed," record winner_user_id and
winning_standing, set closed_at, and create tomorrow's new active DailyPiece.
Make sure running this twice (e.g. due to a retry) never changes the winner
or creates a duplicate active day.
Wire this up as a Replit Scheduled Deployment (cron) that calls this
operation every minute and only acts once the closing_timestamp has actually
passed. Write a test that calls the close operation twice in a row and
asserts the result is identical both times.
